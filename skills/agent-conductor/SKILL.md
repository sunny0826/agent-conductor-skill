# Agent Conductor · Agent 指挥官

按「用户要求 + 模型配置 + 工作说明 → 主 AI → 平台与项目 → 执行动作 → 观察结果 → 判断下一步」组织工作，将判断结果反馈给主 AI。

直接使用下列步骤组织任务与验证结果；解释各层责任或配套技能边界时，读取 [节点与配套边界](references/sources.md)。

## 1. 明确用户要求

从当前消息、已有约定和项目文件提取目标、限制、交付物及可检查的完成条件。区分解释、调查与实施请求。

- 只要求解释或调查时，读取证据并回答，将动作限定为完成回答所需的只读操作。
- 要求实施时，在现有授权范围内推进。先查项目文件和实际状态；只有无法查明且会实质改变结果的信息才提问，同时推进独立工作。
- 保留用户明确指定的人工关口。将“继续做到完成”理解为持续推进已授权工作。
- 用户消息只要求审核、审查、评估或对比时，交付物只有审核报告与结论；实施、修复与派发须等明确的实施指令，不用既有流程惯性或此前授权补全本轮授权。
- 部署、删除数据、共享分支强推等不可逆动作，先核对已有明确授权并遵守宿主审批规则。缺少必要授权时，先完成独立准备再说明关口。
- 对外发送消息必须有明确发送授权，并遵守宿主规则。保护凭证、现有认证和用户改动。用实际理由表达不同意见。

## 2. 调用 agent-conductor-setup 配置模型

读取配套的跨平台 [agent-conductor-setup](../agent-conductor-setup/SKILL.md)，按其步骤以 Lody 接口分页枚举机器、Agent 配置与角色的全部模型，确认可调用的组合。两个技能目录须并排保留。

- 发现刷新条件统一按 [配置约定](../agent-conductor-setup/references/configuration.md) 的"目录刷新条件"执行（快照超 7 天、保存选择失效、宿主或机器变化）；同一会话复用已核对目录。读取项目 `.agent-conductor/models.json`，按该约定的“选择优先级与调用场景”应用角色选择。
- 不读取 Cursor 的目录、规则、模型缓存或接口，不调用其专属代理类型和唤醒命令。
- 可用性分级与"目录不等于已实测"的判定规则见 agent-conductor-setup 第 2 步，此处不重复定义。
- 显式组合用 `machineId + agentConfigId + modelId` 派发；角色用 `agentRoleId` 派发且不传模型覆盖；继承选择省略所有模型覆盖参数。需要在那台机器的本地项目内工作时按 setup 第 5 步传 `workContext`。没有代理工具时由主 AI 自行执行与检查。
- 模型和预算按上述配置约定复用。普通任务建立会话映射即可，用户要求设置或保存时写入中立项目配置。
- 用户仅要求解释原理时无需扫描本机；在此解释场景下，用户追加实际环境检查请求时再执行发现。执行任务时仍按前述规则自动发现。

## 3. 读取工作说明

读取适用于当前路径的项目规则、现有技能和任务步骤，遵守宿主的指令优先级。

区分三类说明：原则规定判断标准，任务步骤规定顺序，专门技能提供具体做法。保持改动最小，查清根因，逐个验证有效单元，检验真实行为。

项目已有匹配的工作指南或技能时，读取并按其要求维护待办和跳过理由。缺少专门说明时，依据目标拟定足够完成任务的步骤，具体操作依据项目约定，不宣称已调用不存在的技能。

从项目规则、贡献指南和 CI 确认适用检查，建立“改动及依赖生成物 → 检查入口 → 责任人”的对应关系。核对源码哈希、目录、Schema 等生成物的依赖；已有统一验收入口时复用，缺少时在本轮范围内复用现有命令，确需持久入口再按项目约定建设。保留未执行项及原因，不为普通改动强制运行全部发布或真机检查。

用户要求解释系统机制、模块归属，或实施前确需澄清现有调用与状态时，按需使用实际可用的 [how](../how/SKILL.md)，先建立有源码依据的运行模型。简单问题直接调查，复杂问题才按能力分工；独立使用不需要模型发现。缺失时沿现有源码调查路径继续并说明证据范围；不将 how 设为所有任务的强制门，不以机制解释代替验收或自动启动修改。

用户要求结构设计，或非平凡变更确需先比较接口、归属和分层方案时，按需使用实际可用的 [architect](../architect/SKILL.md)。先理解现状，从调用者用法推导结构，比较备选并记录取舍；只做设计不自动实施。缺失时沿项目已有设计流程继续，不强制多模型，不以设计批准代替真实行为验收。

先查项目已有的 `verify-<app>` 验收技能或流程，匹配时直接复用。仅在用户要求建立可复用验收，或已授权任务确实需要且缺少此能力时，调用实际可用的 [create-verification-skill](../create-verification-skill/SKILL.md)。生成器可独立使用，无需为了编写验收说明执行本技能的模型发现步骤。生成器缺失时使用现有验证路径，或说明限制；一次性小修改不强制生成，纯解释和只读审查不触发生成或外部副作用。

用户要求影响分析，或任务存在具体跨边界疑点时，按需调用实际可用的 [blast-radius](../blast-radius/SKILL.md)，将已确认风险、有界排除和待证证据用于选择后续验收路径。缺失时说明限制并沿已有分析路径取证；不将它设为每次任务的强制门，也不以影响分析代替 verify 的真实行为验收。该技能可独立使用，无需模型发现。

用户明确要求交叉审核，或具体任务确需多模型排查盲点时，按需调用实际可用的 [interrogate](../interrogate/SKILL.md)。普通审核不强制扩大为多模型；缺少能力时说明降级。setup 负责模型配置，conductor 负责调度，interrogate 负责独立审核与主审裁决，blast-radius 负责影响证明，verify 负责功能验收。审核结论不授权自动修复，也不替代真实用户路径验收。

执行性能测量、报告提速或退化、据数字选型时，按需调用实际可用的 [benchmark-checklist](../benchmark-checklist/SKILL.md)，核验具体性能主张与测量证据。可独立使用，不要求模型发现；缺失时说明限制并沿现有测量路径取证，不成为普通任务强制门。

撰写或润色说明、报告和文档时，按需使用包内 [unslop](../unslop/SKILL.md)，清理套话、术语堆积和机械表达。保留原意、技术名称、引用、数字和证据强度；不为语言风格扩大改动范围或删掉必要的不确定性。

用户要求 TDD、失败测试或回归测试，或错误有明确且低成本的本地检查路径时，按需使用包内 [tdd](../tdd/SKILL.md)。先确认检查因目标错误失败，再修复并用同一检查证明通过；路径不实际时采用有效替代验证，不为普通修改强制搭建测试环境。

按需追溯历史动机时使用包内 [why](../why/SKILL.md)；需要独立方案探索时使用包内 [arena](../arena/SKILL.md)。architect 已连接这两者及包内原则，不另装外部技能。

## 4. 由主 AI 组织任务

由主 AI 维护待办、选择下一步、调用工具、安排分工并对最终结果负责。多写者协作、用户纠正目标或多轮验收时，按 [任务状态对账](references/task-state.md) 维护同一份目标、归属与证据记录；普通单步任务不强制建表。

- 根据依赖拆分任务。独立只读工作可并行；写同一文件或共享实例的工作明确唯一写入者并串行协调，协调者自身也是写入者。交接须先取得旧 owner 的停止回执，再由新 owner 写入；临时帮忙不豁免。
- 宿主支持子任务时再委派。提供目标、范围、禁止事项、输入文件、完成条件、验证方法和报告要求，明确哪些检查由执行者完成、哪些由协调者整合后完成。优先给可访问的文件路径；无法共享文件时提供必要内容。要求执行者按包内技能流程工作时，任务包含该执行者宿主内实际可用的技能路径或内联必要规则，不假设子会话能加载同名技能；不同宿主的技能安装位置不同。
- 派发前用实际命令核对任务包断言的环境事实：分支名与当前 checkout、文件路径存在性、前置产物、角色权限覆盖任务所需操作；条款自检一致——验证命令不与禁止事项冲突、数量与清单一致、他人报告的观察不写成契约，脚本瞬态副作用等已知行为写明豁免。禁止事项用可判定的边界表达（可跑命令、可写路径、豁免项），不把“不要自作主张”类全局压制句当唯一边界。并行写者共享同一 checkout 时，各任务的完成检查限定在自身所有权范围内，全范围检查串行放到集成阶段由协调者执行，不把并行改动造成的失败归为执行者未完成。设计与样式类任务的基准产物（历史原型、设计稿、规范文档）同样属于须核对事实：组件清单、配色与主题值以实际依赖源码为准，当前用法以源码搜索为准；发现基准已过时或与依赖真相冲突时先修正基准，不把过时基准写进任务包。
- 任务包列出目标执行者所需工具的实际状态（已确认／不可用／`unknown`），以及外部操作的已有授权范围、目的地、内容类别和责任人；版本控制操作单独显式授权：git 提交/推送写明禁止、允许或指定分支，缺省视为禁止；未知项明确标注。父会话有工具或目录列出 MCP，不证明子会话能调用。外部保存默认指定一个责任人，其余执行者回传结果；严格只读任务中的外部写入须有明确例外授权。审批拒绝时回传准备内容和原因，不绕过拒绝或换执行者重试同一被拒动作。
- 任务包、计划或范围冻结后的新增条目标注授权来源：用户原话或 Agent 推导。Agent 推导增量先核对是否属于已有授权；超出范围须用户确认，审查通过不能代替授权。已有范围内的增量若改变已审方案，实施前重开同一审查关口，不沿用旧结论。方案增量（新增契约、命令、自动化链路或新交互结构）继承原方案的审查门槛：原方案经独立审查的，增量也须经同级独立审查后才实施；增量大小由审查者判断，协调者不自行认定「增量小可免审」。用户纠正目标后先停止被取代的任务，再更新任务包，不为已派发工作倒推必要性。
- 派发审查时声明目标快照（HEAD、工作树或 diff）。审查期间协调者不改被审范围；确需改动则该轮审查作废，在新快照重开，不把移动目标上的部分结论计为通过。宿主提供结构化审查提交通道时，派发使用能调用该通道的角色；不可用而降级为文本报告时在审查结论中声明。
- 目标交付、撤销或被取代后，取消仍在等待的异步操作；同目标同版本的重复回执合并处理一次并记录。重派或取代旧派发时，旧会话有无落盘写入以实际回执或工作区对账为准，不以宿主重启等间接迹象推断无副作用。已派发任务在执行者闲置或归档而无最终回执时不计为完成，先核对其状态与已落盘产物，再决定补做或重派，不以“据报完成”结案。回执正文截断时读取执行者落盘的完整报告，不以截断结案为"未验证"。保存责任人的通道失败时重试一次，交付时标注未落档项。
- 新工作、修复轮、跟进、重试和下一项队列任务默认使用新代理，带齐原任务、后来要求、上一份报告和分支。
- 只有工作确实需要原代理持有且迁移成本高的本地工作区、未提交改动或仍运行的进程时才续用。向运行中代理下达停止或暂缓指令不算复用。
- 使用 agent-conductor-setup 核对后的 Agent 入口和角色选择。只传宿主接受的参数；继承选择省略模型覆盖。Agent CLI 在本地已安装但宿主没有派发适配器时，保留为发现项，不自行启动推理。
- 读取子任务产物、差异和证据，核对结论并自行写总结。将代理的“已完成”报告作为待检查的输入。

## 5. 核对平台与项目条件

同时检查两层条件，再执行依赖它们的动作。

| 层 | 核对内容 | 缺条件时的处理 |
|---|---|---|
| 平台 | 本次执行者的文件读写、命令、子任务、应用控制、定时或事件唤醒是否实际可用 | 使用能证明同一行为的现有工具；无法替代时说明缺项 |
| 项目 | 工作目录、启动命令、依赖、环境变量、开发数据、已授权账号、验证方法和实例隔离 | 按授权修复基础条件，或记录可复现阻塞；独立工作继续 |

先查仓库文档、脚本和已有验证工具。环境变量只核对名称和配置状态，不输出秘密值。实例无法操作时，先确认进程、端口、版本和授权状态。

持续唤醒来自当前宿主。只有用户要求持续工作且实际存在定时、事件或后台能力时才使用该机制；不要用一次性执行宣称已建立持续唤醒。

## 6. 执行具体动作

使用实际可用的工具完成下一项最小有效动作。操作前确认工作目录、目标文件、实例和授权范围。

- 按项目约定修改文件、运行命令或驱动应用。
- 复用已有 harness 和稳定定位方式，沿真实用户路径操作，避免用内部 setter 或测试专用接口绕过要证明的行为。
- 隔离并行实例；无法隔离时避免同时驱动共享实例。
- 保留与验收相关的命令、输入、输出和产物位置。清理时只清理由本次启动的实例和临时状态，保留证明材料。

日常验收由主 AI 按本次任务选定受影响的功能和入口，verifier 读取项目 verify 技能及功能地图后执行；没有委派能力时由主 AI 承担该职责。回传功能 ID、入口、命令/动作、退出状态、结果、清理后仍可读取的证据位置，以及失败、受阻和未执行项。

整合后由协调者对第 3 步确定的全部适用检查负责，覆盖自己的改动、子任务改动及依赖生成物；记录实际整合版本或 diff、检查入口、退出状态和证据位置。子任务局部检查及全量测试不能替代遗漏的生成物一致性检查。后续改动使检查依据失效时，重验受影响部分。

## 7. 观察实际结果

直接读取实际产物，将操作后的状态与第 1 步的完成条件比较。

- 命令任务检查退出状态及输出文件内容；界面任务执行用户路径并检查结果状态；数据任务读回真实数据和副作用。
- 将日志、截图、返回值与实际行为对应起来。工具成功、编译通过和代理自述各自只证明其可观察的部分。
- 验证失败时先核对观察方法、实例和输入，再定位系统问题。
- 必要且适合脚本化时，运行可复现检查并保留输出。遵守项目检查要求，避免无关重复测试。
- 未执行的检查写明未验证，推断标为推断。报告性能数字时同时说明运行次数、波动与限制因素。

生成 verify 时跑通一个功能，仅证明该生成说明在本次场景可用。不得视作整体验收；未映射、未执行的功能及其他入口不能计为完成。reviewer 的差异审查不能替代 verifier 的真实运行证据，主 AI 仍负责对照本次完成条件判断交付。

## 8. 判断下一步并反馈

根据证据选择状态，将结果反馈到第 4 步。

| 状态 | 判断条件 | 后续动作 |
|---|---|---|
| 继续 | 还有未完成步骤，证据支持下一动作 | 更新待办，执行下一单元 |
| 返工 | 实际结果偏离完成条件，可继续调查或修复 | 记录差异，修正实现或检查方法，重验受影响部分 |
| 交付 | 必需完成条件均有相应证据 | 交付结果、证据和必要限制 |
| 受阻 | 缺授权、能力、环境或关键输入，当前无法补齐 | 保存现场，指出缺项、已尝试动作和恢复条件 |

不要通过降低完成标准结束循环。不要把暂时无进展当作外部阻塞。用户要求停止时，及时停止写入和相关子任务并报告状态。

## 9. 交付可核对的结论

简短说明完成了什么、实际验证了什么、证据在哪里、还有哪些缺口或关口。链接实际生成或读取过的产物。

按当前用户目标逐条对账：每项给出预期、实测场景与结果、回执或证据指针，缺失项列入未验证范围；整体测试通过不能替代逐项对账，也不以"首版已完成"吸收计划里未拿到回执的验收项。小样本、单路径、自审只证明各自范围，不自动替代完整流程或独立审核；未发生的用户审阅不计作证据。使用任务状态表时，完成声明前运行其 `--complete` 检查；失败仍可交付明确标缺口的阶段报告。

解释链路时说明各层责任及失败位置；实施任务时说明改动及用户可观察的结果。区分已完成、未验证和受阻。
