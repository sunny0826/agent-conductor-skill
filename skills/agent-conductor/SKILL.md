# Agent Conductor · Agent 指挥官

按「用户要求 + 模型配置 + 工作说明 → 主 AI → 平台与项目 → 执行动作 → 观察结果 → 判断下一步」组织工作，将判断结果反馈给主 AI。

直接使用下列步骤组织任务与验证结果；解释各层责任或配套技能边界时，读取 [节点与配套边界](references/sources.md)。

## 1. 明确用户要求

从当前消息、已有约定和项目文件提取目标、限制、交付物及可检查的完成条件。区分解释、调查与实施请求。

- 只要求解释或调查时，读取证据并回答，将动作限定为完成回答所需的只读操作。
- 要求实施时，在现有授权范围内推进。先查项目文件和实际状态；只有无法查明且会实质改变结果的信息才提问，同时推进独立工作。
- 保留用户明确指定的人工关口。将“继续做到完成”理解为持续推进已授权工作。
- 用户消息只要求审核、审查、评估或对比时，交付物只有审核报告与结论；实施、修复与派发须等明确的实施指令，不用既有流程惯性或此前授权补全本轮授权。
- 部署、删除数据、共享分支强推等不可逆动作，先核对已有明确授权并遵守宿主审批规则。缺少必要授权时，先完成独立准备再说明关口。
- 对外发送消息必须有明确发送授权，并遵守宿主规则。保护凭证、现有认证和用户改动。用实际理由表达不同意见。

## 2. 调用 agent-conductor-setup 配置模型

确定本轮要派发子任务时才执行本步，主 AI 独自完成时跳过。读取配套的 [agent-conductor-setup](../agent-conductor-setup/SKILL.md)，按其步骤以 Lody 接口分页枚举机器、Agent 配置与角色的全部模型，确认可调用的组合。两个技能目录须并排保留。

- 发现时机统一按 [目录刷新](../agent-conductor-setup/references/configuration.md#目录刷新唯一定义处两个技能共用) 执行。读取项目 `.agent-conductor/models.json`，按该约定的“选择优先级与调用场景”应用角色选择。
- 可用性分级与"目录不等于已实测"的判定规则见 agent-conductor-setup 第 2 步，此处不重复定义。
- 显式组合用 `machineId + agentConfigId + modelId` 派发；角色用 `agentRoleId` 派发且不传模型覆盖；继承选择省略所有模型覆盖参数。需要在那台机器的本地项目内工作时按 setup 第 5 步传 `workContext`。没有代理工具时由主 AI 自行执行与检查。
- 模型和预算按上述配置约定复用。普通任务建立会话映射即可，用户要求设置或保存时写入中立项目配置。
- 用户仅要求解释原理时无需扫描本机；在此解释场景下，用户追加实际环境检查请求时再执行发现。执行任务时仍按前述规则自动发现。

## 3. 读取工作说明

读取适用于当前路径的项目规则、现有技能和任务步骤，遵守宿主的指令优先级。

区分三类说明：原则规定判断标准，任务步骤规定顺序，专门技能提供具体做法。保持改动最小，查清根因，逐个验证有效单元，检验真实行为。

项目已有匹配的工作指南或技能时，读取并按其要求维护待办和跳过理由。缺少专门说明时，依据目标拟定足够完成任务的步骤，具体操作依据项目约定，不宣称已调用不存在的技能。

按 [当前技能读取与采用核验](references/skill-adoption.md) 从本次目录选技能、核对权威源与执行机器的实际内容，再提取本次要求制定计划。角色和计划不固定技能版本或复制长期流程。阶段切换、重新派发及发现必要引用更新时重读受影响内容；已安装不等于已确认最新，已读取不等于实际采用。协调者组织完整流程，参与者只承担已分配阶段，不因技能要求协作而自行派发。

从项目规则、贡献指南和 CI 确认适用检查，建立“改动及依赖生成物 → 检查入口 → 责任人”的对应关系。核对源码哈希、目录、Schema 等生成物的依赖；已有统一验收入口时复用，缺少时在本轮范围内复用现有命令，确需持久入口再按项目约定建设。保留未执行项及原因，不为普通改动强制运行全部发布或真机检查。

下列技能都按需使用，不是每次任务的强制门，可独立使用，无需模型发现。技能缺失时说明限制并沿现有路径继续，不宣称已调用。setup 负责模型配置，conductor 负责调度，interrogate 负责独立审核与主审裁决，blast-radius 负责影响证明，verify 负责功能验收。

| 需要 | 使用 | 何时使用 | 边界 |
|---|---|---|---|
| 理解机制与归属 | [how](../how/SKILL.md) | 用户要求解释，或实施前确需澄清现有调用与状态 | 先建立有源码依据的运行模型；简单问题直接调查，复杂问题才按能力分工；不代替验收，不自动启动修改 |
| 结构设计 | [architect](../architect/SKILL.md) | 用户要求，或非平凡变更确需比较接口、归属和分层 | 从调用者用法推导结构并记录取舍；只做设计不自动实施；不强制多模型；设计批准不代替行为验收 |
| 功能验收 | 项目 `verify-<app>`，缺失时 [create-verification-skill](../create-verification-skill/SKILL.md) | 先查已有 verify 并复用；仅用户要求建立，或已授权任务确需且缺失时生成 | 一次性小修改不强制生成；纯解释和只读审查不触发生成或外部副作用 |
| 影响分析 | [blast-radius](../blast-radius/SKILL.md) | 用户要求，或存在具体跨边界疑点 | 已确认风险、有界排除和待证证据用于选择验收路径；不代替 verify |
| 交叉审核 | [interrogate](../interrogate/SKILL.md) | 用户明确要求，或具体任务确需多模型排查盲点 | 普通审核不扩大为多模型；缺能力时说明降级；结论不授权自动修复，不替代用户路径验收 |
| 性能主张 | [benchmark-checklist](../benchmark-checklist/SKILL.md) | 执行性能测量、报告提速或退化、据数字选型 | 核验具体主张与测量证据 |
| 文字清理 | [unslop](../unslop/SKILL.md) | 撰写或润色说明、报告和文档 | 保留原意、技术名称、引用、数字和证据强度；不为风格扩大改动或删掉必要的不确定性 |
| 回归检查 | [tdd](../tdd/SKILL.md) | 用户要求 TDD、失败测试或回归测试，或错误有明确且低成本的本地检查路径 | 先确认检查因目标错误失败，再修复并用同一检查证明通过；路径不实际时用有效替代验证 |
| 历史动机／方案探索 | [why](../why/SKILL.md)／[arena](../arena/SKILL.md) | 按需追溯动机，或需要独立方案探索 | architect 已连接这两者及包内原则，不另装外部技能 |

## 4. 由主 AI 组织任务

由主 AI 维护待办、选择下一步、调用工具、安排分工并对最终结果负责。多写者协作、用户纠正目标、多轮验收，或计划声明了实施后的审查/验证关口时，按 [任务状态对账](references/task-state.md) 维护同一份目标、归属与证据记录；关口及其回执状态作为验收项入表，交付声明前跑该文件的 `--complete` 检查收口，未拿到回执的关口不得以阶段完成吸收。普通单步任务不强制建表。

- 根据依赖拆分任务。独立只读工作可并行；写同一文件或共享实例的工作明确唯一写入者并串行协调，协调者自身也是写入者。交接须先取得旧 owner 的停止回执，再由新 owner 写入；临时帮忙不豁免。
- 宿主支持子任务时再委派。每次派发前读取 [派发契约](references/dispatch.md)，它定义任务包内容、派发门、事实核对、工具授权和审查快照。任务包落盘为文件，首行声明类型；发送前用 `node <本技能目录>/scripts/dispatch-gate.mjs pre <package.md> <message.md>` 检查到退出 0；发送已检查文件的原文；发送后运行同一脚本的 `post`。实验、重放和用户指定的 MCP 派发都不豁免。
- 任务包、计划或范围冻结后的范围决定（新增、收缩或降级）标注授权来源：用户原话或 Agent 推导；与用户指令或已确认方案有出入的取舍逐项列出，派发前不静默吸收。Agent 推导增量先核对是否属于已有授权；超出范围须用户确认，审查通过不能代替授权。已有范围内的增量若改变已审方案，实施前重开同一审查关口，不沿用旧结论。方案增量（新增契约、命令、自动化链路或新交互结构）继承原方案的审查门槛：原方案经独立审查的，增量也须经同级独立审查后才实施；增量大小由审查者判断，协调者不自行认定「增量小可免审」。用户纠正目标后先停止被取代的任务，再更新任务包，不为已派发工作倒推必要性。
- 目标交付、撤销或被取代后，取消仍在等待的异步操作；同目标同版本的重复回执合并处理一次并记录。progress 流、已转达、已派发等中间信号只作进行中汇报，完成声明与验证结论绑定最终回执并指明验证主体，协调者自验标注为自验。用户新消息与子任务回执同时到达时，先回答用户消息，再汇报回执；不把完成/失败回执或“缺少某工具”当作对用户当前请求的回答，用户要求的截图、验收、测试和解释先给可执行答复或具体阻塞。重派或取代旧派发时，旧会话有无落盘写入以实际回执或工作区对账为准，不以宿主重启等间接迹象推断无副作用。已派发任务在执行者闲置或归档而无最终回执时不计为完成，先核对其状态与已落盘产物，再决定补做或重派，不以“据报完成”结案。回执正文截断时读取执行者落盘的完整报告，不以截断结案为"未验证"。保存责任人的通道失败时重试一次，交付时标注未落档项。审查/验证派发在任务状态表记录等待窗；超过等待窗仍无 assistant 文本或落盘产物，按零回执处理，先取消旧会话再切换，不等待宿主杀进程。
- 新工作、新阶段、跟进、重试和下一项队列任务默认使用新代理，带齐原任务、后来要求、上一份报告和分支。同一返工循环内的连续修复轮优先续用原执行者，保留问题上下文；审查与验证轮次仍用新会话保持独立。执行者零回执且无落盘产物的失败，同一角色或模型配置最多重试一次，仍无产出即更换角色或配置，或按降级条款交付，不重复派发同一配置。故障切换从已核对目录中选择同职责的可用配置即可，不视为替用户新增模型选择；交付中标明更换原因。只有引入新预算/推理档位或用户指定的角色时才需用户确认。
- 同一返工循环的修复轮按上一条续用。其他任务仅在确需原代理持有且迁移成本高的本地工作区、未提交改动、仍运行的进程，或复核须依赖原代理上轮发现时续用；续用复核须在任务包与交付中标明，不能计为新会话独立审查。向运行中代理下达停止或暂缓指令不算复用。
- 使用 agent-conductor-setup 核对后的 Agent 入口和角色选择。只传宿主接受的参数；继承选择省略模型覆盖。Agent CLI 在本地已安装但宿主没有派发适配器时，保留为发现项，不自行启动推理。
- 读取子任务产物、差异和证据，核对结论并自行写总结。将代理的“已完成”报告作为待检查的输入。
- 任务包列出适用技能入口、选择理由和应回传的采用证据，不硬编码长期版本或把旧步骤当作现行规则。执行者读取其宿主当前内容后形成任务要求；协调者核对漏选、误触发、缺执行和缺证据，在同一任务记录的 `skill_review` 中收口。具体字段与完成门槛使用 [采用核验契约](references/skill-adoption.md)，不能只以出现技能名计作采用。

## 5. 核对平台与项目条件

同时检查两层条件，再执行依赖它们的动作。

| 层 | 核对内容 | 缺条件时的处理 |
|---|---|---|
| 平台 | 本次执行者的文件读写、命令、子任务、应用控制、定时或事件唤醒是否实际可用 | 使用能证明同一行为的现有工具；无法替代时说明缺项 |
| 项目 | 工作目录、启动命令、依赖、环境变量、开发数据、已授权账号、验证方法和实例隔离 | 按授权修复基础条件，或记录可复现阻塞；独立工作继续 |

先查仓库文档、脚本和已有验证工具。环境变量只核对名称和配置状态，不输出秘密值。实例无法操作时，先确认进程、端口、版本和授权状态。

持续唤醒来自当前宿主。只有用户要求持续工作且实际存在定时、事件或后台能力时才使用该机制；不要用一次性执行宣称已建立持续唤醒。关键路径上的异步结果（远端 CI、后台验证、长时测试）未回时不要停摆：用户已要求持续推进时，在回合内用阻塞等待或完成通知跟进到可判定状态再继续；确需交还回合时说明需要用户何时再触发，不以“完成前不来找用户”代替推进。

## 6. 执行具体动作

使用实际可用的工具完成下一项最小有效动作。操作前确认工作目录、目标文件、实例和授权范围。

- 按项目约定修改文件、运行命令或驱动应用。
- 复用已有 harness 和稳定定位方式，沿真实用户路径操作，避免用内部 setter 或测试专用接口绕过要证明的行为。
- 隔离并行实例；无法隔离时避免同时驱动共享实例。
- 保留与验收相关的命令、输入、输出和产物位置。清理时只清理由本次启动的实例和临时状态，保留证明材料。

日常验收由主 AI 按本次任务选定受影响的功能和入口，verifier 读取项目 verify 技能及功能地图后执行；没有委派能力时由主 AI 承担该职责。回传功能 ID、入口、命令/动作、退出状态、结果、清理后仍可读取的证据位置，以及失败、受阻和未执行项。

整合后由协调者对第 3 步确定的全部适用检查负责，覆盖自己的改动、子任务改动及依赖生成物；记录实际整合版本或 diff、检查入口、退出状态和证据位置。子任务局部检查及全量测试不能替代遗漏的生成物一致性检查。后续改动使检查依据失效时，重验受影响部分。

## 7. 观察实际结果

直接读取实际产物，将操作后的状态与第 1 步的完成条件比较。

- 命令任务检查退出状态及输出文件内容；界面任务执行用户路径并检查结果状态；数据任务读回真实数据和副作用。
- 将日志、截图、返回值与实际行为对应起来。工具成功、编译通过和代理自述各自只证明其可观察的部分。
- 验证失败时先核对观察方法、实例和输入，再定位系统问题。
- 必要且适合脚本化时，运行可复现检查并保留输出。遵守项目检查要求，避免无关重复测试。
- 未执行的检查写明未验证，推断标为推断。报告性能数字时同时说明运行次数、波动与限制因素。

生成 verify 时跑通一个功能，仅证明该生成说明在本次场景可用。不得视作整体验收；未映射、未执行的功能及其他入口不能计为完成。reviewer 的差异审查不能替代 verifier 的真实运行证据，主 AI 仍负责对照本次完成条件判断交付。

## 8. 判断下一步并反馈

根据证据选择状态，将结果反馈到第 4 步。

| 状态 | 判断条件 | 后续动作 |
|---|---|---|
| 继续 | 还有未完成步骤，证据支持下一动作 | 更新待办，执行下一单元 |
| 返工 | 实际结果偏离完成条件，可继续调查或修复 | 记录差异，修正实现或检查方法；违反同一条规则的问题在触及范围内全量修复，不只修被点名项；按第 3 步的检查映射重验受影响部分与对应回归。全量验收仅在项目要求、用户明确要求或定向检查无法覆盖影响时执行，不因返工、提交 PR 或交付自动触发 |
| 交付 | 必需完成条件均有相应证据 | 交付结果、证据和必要限制 |
| 受阻 | 缺授权、能力、环境或关键输入，当前无法补齐 | 保存现场，指出缺项、已尝试动作和恢复条件 |

不要通过降低完成标准结束循环。不要把暂时无进展当作外部阻塞。用户要求停止时，及时停止写入和相关子任务并报告状态。

## 9. 交付可核对的结论

简短说明完成了什么、实际验证了什么、证据在哪里、还有哪些缺口或关口。链接实际生成或读取过的产物。

按当前用户目标逐条对账：每项给出预期、实测场景与结果、回执或证据指针，缺失项列入未验证范围，与用户指令或已确认方案有出入的范围决定逐项列出；整体测试通过不能替代逐项对账，也不以"首版已完成"吸收计划里未拿到回执的验收项。小样本、单路径、自审只证明各自范围，不自动替代完整流程或独立审核；未发生的用户审阅不计作证据。用户笼统回复「验收通过」「没有问题了」只证明用户认可当前状态，不替代验收清单逐项回报；清单中未明确确认的项仍列为未验证，不能用合并或后续阶段完成吸收。也不得把笼统通过扩写成具体项的通过：此前明确尚未执行的检查（如步行测试、断电恢复）仍写未验证，不能因为用户说了「验证通过」就改写成「该项通过」。用户消息是用户确认的唯一来源；串口、日志、截图和测试退出码只能写成设备或产物证据。要写「你已确认」「你的目视确认」，必须同时引用用户原话；没有原话就写「用户未逐项确认，当前证据来自…」。前次交付标注的未验证项在后续交付中保留，直到取得证据关闭；后续其他检查通过不能吸收尚未关闭的缺口。使用任务状态表时，完成声明前运行其 `--complete` 检查；失败仍可交付明确标缺口的阶段报告。交付正文标明验证主体：子会话完成的检查写执行者与回执，不写成协调者自己核对；协调者只对自己的实测标注自验。

解释链路时说明各层责任及失败位置；实施任务时说明改动及用户可观察的结果。区分已完成、未验证和受阻。
