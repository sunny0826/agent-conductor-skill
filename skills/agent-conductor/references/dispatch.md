# 派发契约

每次创建子会话前读取本页。实验、重放、对比和临时验证只要创建子会话就算派发。用户指定用 MCP 或其他工具派发时，本页要求同样适用。

## 任务包内容

任务包提供目标、范围、禁止事项、输入文件、完成条件、验证方法、报告要求、执行身份（被派会话自身执行，确需再分工先回报协调者重派）和最终回执的投递地址，并写明哪些检查由执行者完成、哪些由协调者整合后完成。优先给可访问的文件路径；无法共享文件时提供必要内容。

- 任务包断言的代码现状由执行者动手前自行核对。断言与实际代码不符时，执行者停止并回报，不按断言修改代码。
- 要求执行者按包内技能流程工作时，任务包写明该执行者宿主内实际可用的技能路径或内联必要规则。不同宿主的技能安装位置不同，不假设子会话能加载同名技能。
- 禁止事项用可判定的边界表达：可跑命令、可写路径、豁免项。“不要自作主张”这类全局压制句不作任务包边界或开场指令。
- 任务包默认落盘为文件，首行声明类型：`任务包类型：实施`、`任务包类型：只读审查` 或 `任务包类型：验证`。声明值仅限这三个，既实施又验证的声明实施。包文件保留到该任务验收关闭，不放会被自动清理的临时目录。
- 无法与执行者共享文件时内联任务包并提供全部条款，此时检查对象是任务包全文，不是引导句。
- 派发消息只写包指针与回执要求，不承载边界条款。指针只应指向包文件，消息里顺带出现的其他 `.md` 路径不算指针。

技能源在会话中途更新（用户告知、部署副本被同步或本会话写入修改）后，下一次派发前重读技能文本再组织任务包。长会话在每次派发前比较部署副本 `SKILL.md` 的哈希与该会话首次读取时的值，变化则先重读。重读技能文本不替代下面的派发门。

## 派发门

```sh
GATE=<agent-conductor目录>/scripts/dispatch-gate.mjs
node "$GATE" pre <package.md> <message.md>      # 发送前：包、消息、指针
node "$GATE" pre --inline <message.md>          # 内联任务包：同一文件按包和消息检查
node "$GATE" post <message.md> --session <id>   # 发送后：比对子会话首条消息
node "$GATE" post --session <id>                # 没有消息文件时：检查落盘首条消息
```

退出码：`0` 通过；`1` 违规；`2` 无法核实。

1. 修正到 `pre` 退出 0 后再派发。包检查覆盖类型缺失、声明值错误、声明行位置或重复、声明与授权词面冲突、压制句、实施类缺执行身份或失败基线、缺回执要求、审查与验证类缺命令边界。消息检查覆盖缺包指针、缺回执要求、压制句和禁令条款。`pre` 还核对消息确实指向传入的包文件。
2. 已检查的消息文件就是发送正文。宿主支持文件入参时直接发送该文件（Lody：`lody session create|chat ... --prompt-file <message.md>`）。工具只接收字符串时，把文件内容原样传入，再把最终文本跑一次 `check-dispatch.mjs --message -`。不得手工转抄，也不得在正文前后追加开场白或压制句。
3. 创建前必须拿到一份 `pre` 通过的消息文件。没有消息文件就直接创建会话，视为未通过派发门；`post --session` 只补上落盘复核，不替代创建前的检查。
4. 派发后立即运行 `post`。退出码 1 表示消息违规或发送污染：取消该子会话，更新消息文件并重新检查后重发，不复用旧文件，也不手工插入新句。退出码 2 表示无法核实：保留证据缺口，核对发送时的角色前缀或读取故障，不据此取消或认定通过。
5. 宿主会给带 `promptPrefix` 的 Agent Role 在正文前注入该前缀。脚本按子会话的 `agentRoleId` 读取角色配置，比对前去掉已配置前缀；读取不到时用 `--role-prefix` 显式提供。除已配置的角色前缀外，发送时新增前缀、改写或缺少已检查文件都视为发送污染。

## 派发前核对事实

用实际命令核对任务包断言的每类事实。无法核对的标注由执行者核对，或不写入。

- 环境：分支名与 checkout、路径存在性、上游依赖状态、基线新鲜度。fetch 后 pin 基线 commit，不以过时本地 HEAD 充当最新基线。
- 真实数据样本：依赖历史产物或外部数据时，先取真实样本核对字段与内容存在性，不基于假想数据形状设计链路。构造样本只能用于单元测试，不能作为真实链路通过的验收证据。
- 项目静态约束：行数、函数规模、退出码等完成定义，随任务包下发并由执行者交付前自检。
- 前置产物与其运行态，以及角色权限是否覆盖任务所需操作。
- 对他会话已完成动作的断言（如“你已审查”）须与该会话实际回执一致；记录不可读时不写断言。
- 设计与样式类任务的基准产物（历史原型、设计稿、规范文档）：组件清单、配色与主题值以实际依赖源码为准，当前用法以源码搜索为准。发现基准已过时或与依赖真相冲突时先修正基准，不把过时基准写进任务包。

验收脚本先自证断言失败会以非零退出，再采信其通过结果；验证脚本自身不可信时先修脚本。

条款自检一致：验证命令不与禁止事项冲突，数量与清单一致，他人报告的观察不写成契约，脚本瞬态副作用等已知行为写明豁免。

完成检查与执行者修复权一致：

- 派发时记录失败基线，完成判定为相对基线无新增失败。预存失败列出不修，失败源在所有权外的留给集成阶段。
- 并行写者共享同一 checkout 时，全范围检查串行放到集成阶段由协调者执行，各任务的完成检查限定在自身所有权范围内，不把并行改动造成的失败归为执行者未完成。

## 工具与外部操作

任务包列出目标执行者所需工具的实际状态（已确认／不可用／`unknown`），以及外部操作的已有授权范围、目的地、内容类别和责任人。父会话有工具或目录列出 MCP，不证明子会话能调用。

版本控制操作单独显式授权：git 提交／推送写明禁止、允许或指定分支，缺省视为禁止；未知项明确标注。外部保存默认指定一个责任人，其余执行者回传结果。严格只读任务中的外部写入须有明确例外授权。审批拒绝时回传准备内容和原因，不绕过拒绝或换执行者重试同一被拒动作。

## 审查与验证派发

派发审查时声明目标快照（HEAD、工作树或 diff）。审查期间协调者不改被审范围；确需改动则该轮审查作废，在新快照重开，不把移动目标上的部分结论计为通过。

审查与验证类任务包写明命令执行边界（允许执行的命令及瞬态副作用豁免，或明确不执行任何命令），不单用“只读”承载验证深度。

宿主提供结构化审查提交通道时，派发使用能调用该通道的角色，并先核对身份前提：通道按会话身份挂接时，角色可用不证明能调用。可预检则核对；不可预检或核对不过时，在任务包预写降级条款（调用失败即文本报告并在结论中声明）。身份类失败按降级条款交付，内容格式类失败修正后重试一次再降级。
