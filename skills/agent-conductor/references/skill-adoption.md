# 当前技能读取与采用核验

角色提示词保留职责、权限、技能入口和证据责任；流程与具体要求以本次读取的技能为准。角色与计划不固定技能版本号或提交，不复制整份技能作为长期规则，也不把本页当成每次必须加载全部技能的清单。

需要修改角色配置时使用 [角色接入说明](role-integration.md) 与其共用模板，保留角色原有职责和授权约束。

## 开工时选择和读取

1. 协调者从用户目标、角色职责和当前宿主技能目录判断候选，记录目录证据和选择理由；执行者再核对实际可读性与适用性。不能只凭执行者自报的名单检查是否漏用。只记录相关候选和容易混淆的排除项，不为凑使用率调用技能。
2. 定位项目指定的权威技能源与执行机器的安装位置。本项目以源仓库为准；核对当前源内容和所需引用、脚本，不把本地文件存在、历史摘要或旧同步回执当作“当前最新”的证明。本轮获授权修改的工作树可作为本轮依据，但标明未发布，不能称其他宿主已同步。
3. 在已有同步授权内更新安装内容，读取实际使用的 SKILL.md 及本任务需要的引用。记录来源、读取时间、读取证据和内容核对依据。只读说明不授予安装、全局配置、提交或推送权限；无法读取或无法确认最新内容时保留缺口，不静默使用旧文本并声称最新。
4. 从刚读取的内容提取本次适用要求，写入当前任务的执行计划。技能更新后要求可能变化，不能在检查器中硬编码某个技能的永久步骤，也不能仅以关键词出现证明采用。技能名只是入口；改名或移除时回到当前目录重新选择，不猜测同名替代。
5. 长任务在阶段切换、重新派发或发现技能及其必要引用更新时重新核对、重读，调整受影响的未完成步骤。已经完成的阶段保留当时要求和证据；如新要求影响尚未成立的交付条件，补验相关部分。不得用后来要求追溯判定历史违规，或靠改写旧要求让检查通过。

同步状态和规则内容属于任务证据，不是固定版本配置。技能更新也不扩大任务范围、预算或操作授权；新增派发沿用现有确认关口。

## 组织者与参与者

技能描述的完整流程可以跨多个角色。由协调者承担组织、派发、结果整合和最终判断；受委派的架构师、worker、审查者及 writer 只执行分配给本会话的阶段。

参与者遇到创建候选、邀请评判、交叉审核或独立验证等要求时，回报所需职责、原因和产物，由协调者按已有授权安排。工具存在、技能写了派发步骤、宿主建议求助，都不赋予执行者派发权。只完成一个候选或一份审核报告时，不声称完整 Arena、Swarm 或跨模型审核已经完成。

## 在同一份任务记录中留证

使用 [任务状态对账](task-state.md) 的 `tasks[].skill_review`，由协调者唯一维护；执行者回传事实与证据，不另写一份竞争的任务状态。单会话任务由当前主会话承担记录和核验，明确为自验。普通单步任务可保留同等信息的简短回执，不强迫搭建完整任务表；已有任务表或正式采用审计则使用本契约。

```json
{
  "assessed_by": "负责核对选择的协调者或当前主会话",
  "catalog_evidence": ["本次宿主目录或技能索引的实际读取记录"],
  "selection_reason": "根据任务与当前触发条件选择这些技能的理由",
  "skills": [
    {
      "name": "本次选定的技能名",
      "applicability": "required",
      "reason": "本任务满足的触发条件",
      "reading": {
        "sources": ["实际 SKILL.md 路径及本次必要引用"],
        "read_at": "实际 ISO 时间，包含时区",
        "evidence": ["工具读回或宿主完整注入内容的记录"],
        "freshness": {
          "status": "confirmed",
          "reason": "权威源和实际读取内容的核对方式",
          "evidence": ["本次内容核对或同步后读回的记录"]
        }
      },
      "requirements": [
        {
          "id": "R1",
          "expected": "从当前内容提取的本次可核验要求",
          "status": "pending",
          "observed": "",
          "evidence": []
        }
      ]
    }
  ]
}
```

字段填写实际事实，示例说明不能直接当证据。`skills: []` 仅在核对当前目录后确无匹配时使用，仍需选择理由、核对者和目录证据。相关候选不适用时写 `applicability: "not_applicable"`、具体 `reason` 和空 `requirements`；无需为排除明显不适用技能而读取所有正文。

选定技能尚未读到时可暂不填 `reading`；已读取但无法核对权威源时，`freshness.status` 写 `unconfirmed`，写明原因并保留已有证据。两者均不能通过采用完成检查。

要求的状态：

| status | 含义与证据 |
|---|---|
| `pending` | 尚未执行；允许空结果与证据 |
| `applied` | 已执行待核验；必须有具体 `observed` 和动作或产物证据 |
| `verified` | 核验者已读回证据并认可；另附 `review.by` 和 `review.evidence` |
| `not_applicable` | 本次角色或场景不适用该条要求；`observed` 写原因，核验者以 `review` 记录依据 |
| `blocked` | 无法继续；`observed` 写具体缺口，不当作已采用 |

`review.evidence` 指向核验判断及依据，不能仅重复“已采用”。同一人自验可记录，但不冒充独立审查。全部要求均被排除时重新判断技能是否适用，不把空执行计入采用。

技能选择原因、已读取、实际采用与采用已核验分别成立；不维护可与要求状态矛盾的总 `used: true`。一项选定技能只有读取来源和最新内容已确认，且所有适用要求均核验通过，才可计入已验证采用。

## 完成检查与实际证据

在任务开工前核对选择与计划；执行者回传后，协调者逐项检查要求与原始证据。最后运行原有 `check-task-state.mjs <task-state.json> --complete`，不用新建第二套状态文件。

检查器验证字段、来源与读取记录、证据引用、要求状态及核验记录。它不访问 Lody、不执行证据命令、不理解技能语义，不能证明引用内容真实，也不能自动发现被隐去的候选或要求。协调者必须对照当前目录、当时读到的完整要求、任务范围和实际产物检查遗漏；新增独立核验仍按派发授权安排。检查器失败可交付诚实的阶段结果，不能宣称采用验收完成。

例如：当前 tdd 要求修复前失败、修复后同一检查通过时，核验两次命令、目标错误和结果；只有修复后通过不足以证明采用。文档技能则核对实际文本、读者目标和需要的步骤，不编造不存在的运行日志。

## 任务后审计

复用已有会话与任务记录，不自动创建定时任务或额外 Agent。按当时适用要求抽查：应触发却漏选、读了却未执行、声称采用却证据不足，以及不适用却强制使用。统计分母是本应触发的任务，不是全部任务或技能总数；没有可靠分母时列出实例和未知范围，不编造采用率。历史会话缺读取或采用证据时记为“未证明”，不能直接断言没有使用。
