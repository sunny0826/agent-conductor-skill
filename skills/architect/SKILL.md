# Architect · 结构设计

交付有依据的结构草图与取舍。先说明调用者怎样使用，再定义类型、签名、状态归属与模块边界；实现持续暴露设计是否成立。

## 1. 明确目标并理解现状

从请求确定问题、约束、完成条件和设计／实施范围，保留用户明确指定的评审关口。先读项目事实，只有无法观察且会改变方案的信息才询问。

用包内 [how](../how/SKILL.md) 建立入口、数据流、状态拥有者、调用方与外部边界的运行模型。设计改变归属或分层时核对历史约束；包内 [why](../why/SKILL.md) 按需取证，不猜作者动机。真正无周边集成的全新系统可省略现状追踪，并注明原因。

记录设计基于的版本与相关未提交内容。审阅范围仅限所需代码和材料，不读取秘密或无关会话。设计任务只写已授权的设计产物，不将产品替换成未实现的脚手架。

## 2. 比较结构方案

先固定共同问题、约束和判定标准，再按 [设计请求](references/runner-prompt.md) 产出候选。非平凡设计至少考虑两个结构上不同的方案，差异应在状态归属、模块边界或接口结构，不能只换名称。若约束排除了其他形状，说明被排除的具体方案与证据，不伪造第二个可行候选。

按包内 [arena](../arena/SKILL.md) 执行共同问题、独立候选、候选完成后的独立评判、选基础、吸收与验证六阶段，使用 [设计请求](references/runner-prompt.md)。复用宿主已有角色与模型选择；能力不足明确缺失阶段，主会话顺序比较仅是设计草案，不是独立探索或完整 Arena。

按 [结构风险检查](references/design-red-flags.md) 检查相关风险。候选和协调者读取 [设计原则](references/principles.md)，按问题选择适用约束，不强制不相关原则。主 AI 阅读所有完整候选与评判，核对假设并记录分歧；失败候选不视为赞同。

## 3. 写出结构与取舍

参照 [设计记录](references/rationale-template.md)，保留调用者用法、核心类型与签名、模块和数据流、约束编码位置、备选方案、基础方案选择及吸收／拒绝理由。图解适用于跨模块关系，文字与图须一致。

草图中的未实现逻辑明确标注，不冒充可运行产物。接口从真实用例推导，必要的两三个调用示例即可；小设计不为凑栏目增加模块或文档。契约、错误、异步完成和清理应与实际任务相关。

仅要求设计时交付到此。已授权实施则按选定结构继续，无需增加默认审批关口；用户要求“先展示、等确认”时必须保留该关口。需要对抗审核时按需使用包内 [interrogate](../interrogate/SKILL.md)，不将它设为每次设计的强制门。

## 4. 在授权范围内实施与验证

以选定设计为契约，按可验证单元填入逻辑。核对真实调用者及数据路径，记录必要偏离；不要为了守住草图而强行加参数、共享状态或补丁。

实施后使用项目既有验收、测试或项目生成的 verify（项目未生成时直接验证真实行为，不要求外部 SKILL） 核对真实行为。类型检查、设计图及编译成功只证明局部事实。缺运行条件时标明未验证，不将设计认可写成产品完成。没有实施授权时，本节不执行。

## 5. 设计不成立时重新探索

重复的跨模块绕行、多个同形特殊分支、频繁类型逃逸、调用者依赖内部细节或意外共享写入，是重新核对结构的信号。单个复杂边界不自动判设计失败；先判断约束遗漏、实现偏离还是形状错误。

确认结构错误后，保留失败证据，重建已实现部分的运行模型，将新约束纳入共同问题，移除本轮被替代的冗余后回到方案比较。只在已有授权范围内调整，保护用户改动；不扩大成无关重构。

交付选定结构、取舍、设计与实施状态、验证范围、未知项和下一步。设计调用不自动授权提交、推送、发布或修改全局配置。来源与适配见 [来源说明](references/sources.md)。
