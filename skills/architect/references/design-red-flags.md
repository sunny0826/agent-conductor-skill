# 结构风险检查

按实际调用者和任务约束判断；这些是调查线索，不是必须重构的风格门槛。指明具体路径、影响与取舍，再决定保留、修改或排除。

| 信号 | 需要核对 |
|---|---|
| 接口大、隐藏复杂度少 | 调用者是否必须协调内部阶段，或理解实现才能完成一次操作？ |
| 内部信息扩散 | 同一协议、存储或框架决策是否出现在多个边界，改变时必须同步修改？ |
| 按执行顺序拆层 | load/validate/transform/save 是否重复拥有同一表示和不变量，而非各自保护明确知识？ |
| 无职责的透传 | 包装是否只转发同形参数？它是否提供必要策略、适配或边界？ |
| 状态归属分裂 | 谁能写同一状态，副本如何一致？能否分离写入者，或让唯一拥有者执行变更？ |
| 多条完成路径 | 是否存在可误用的旧入口和新入口？迁移、兼容要求是否支持保留？ |
| 可绕过公共接口 | 外部能否导入内部模块，破坏封装？构建或类型边界是否能阻止实际误用？ |
| 手工同步清单 | 相同项目是否在多个位置独立维护？能否派生或用实际检查检测偏离？ |

接口深度指公共表面所隐藏的复杂度，不是调用层级的深度。减少调用链的目的在于降低理解成本，不以固定文件数判定架构好坏。类型、检查与文档各有边界，不为了“无法误用”过度扩大工程范围。
