# 把重复错误变成结构约束

阅读本任务所需的提交、回退、评审和项目规则，按错误类别归并。至少两次实际出现才认定重复类别；引用具体证据，不把一次个人偏好当作全仓库约束。

1. 优先通过架构消除：单一状态拥有者、一个受支持入口、隐藏内部实现、一个事实来源、删除诱导错误的旧路径。
2. 其次通过类型表达合法状态；仍能编译的错误用 lint／CI 检查阻止，错误消息指出正确文件、类型或函数。已有大量遗留时可只阻止新增，不扩大无关迁移。
3. 测试可观察行为，遵守包内 [行为测试](../principle-test-behavior-not-implementation/SKILL.md)。行为坏了仍通过，或只改内部实现就失败的测试，应修正或删除。
4. 文档和 Agent 规则最后写，只记录结构无法判定的判断要求。

先处理最常见的真实类别，逐项证明新机制对真实过去错误失败、对修复后状态通过。用一致的本地和 CI 检查入口；没有 CI 运行条件就标未验证。异常例外须有行内原因、到期时间和明确人工许可，不能借口流程新建批准者。

维护“规则—执行机制”对应表；已有规则又犯错说明机制不足，应提升执行层级，错误不再可能发生时删掉无用提示。按 [结构编码](../principle-encode-lessons-in-structure/SKILL.md) 选择机制。每类可独立交付，但只在已有授权下提交或修改全局规则。

交付各类别证据、选定层级、未用更高层级的原因、失败／通过证明和剩余范围。
