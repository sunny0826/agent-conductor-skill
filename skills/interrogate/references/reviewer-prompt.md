# 统一审核请求

派发前将下面内容填实，同一份客观请求交给每位独立审阅者（只附事实、快照与完成条件，不塞入长篇作者自辩亮点或诱导挑刺清单）。补充证据时同步给所有需要复核的审阅者，记录快照变化。

> 请独立审核所附证据，判断实现是否满足用户意图。审核对象只读；不要修复或执行有副作用的操作。首轮不读取其他审阅者报告；复审仅核验上轮已采纳阻塞项是否修复及本轮增量 diff 是否引入回归，不围绕防御补丁构造二阶极限反例（若补丁过度复杂，建议回退并收窄边界）。无现实可达的阻塞缺陷时明确给出可合并（Approve）结论，允许零发现；无法完成请报告原因，不以零发现代替失败。
>
> 用户意图、约束、可核验完成条件：填写本次事实（含避免过度防御等项目约束）。
>
> 审核范围：填写实际基线、HEAD、工作树／暂存区／新增文件的包含情况、快照标识与指纹清单。
>
> 证据：附同一份 diff、相关文件和调用上下文；说明可读取边界、缺失上下文及不可验证范围。
>
> 权限：填写宿主实际限制及是否允许隔离临时证明；只读提示不代表系统沙箱。未明确授权执行时做静态审核。
>
> 判定标准：应用下面与本次变更相关的维度，遵守所附项目规则，不新增全局门槛，不为极低概率或人工对抗布景堆砌防御复杂度。
>
> 报告：严分「阻塞项（Must fix）」与「非阻塞观察（Nit / Non-blocking）」。每条给出具体文件行号或函数、正常用户/调用方可达的输入与路径、影响与严重程度及其理由、证据和缺口、可选建议。依赖手工篡改受管文件、自残参数、矛盾环境变量、亚秒级掉包或多重罕见故障叠加的场景（即使探针可复现）一律归入非阻塞观察。注明实际检查范围、命令和退出码（若执行）。保留原始报告，即使没有发现。

## 共同判定标准

- 正确性：行为是否符合完成条件；按相关性检查边界、错误传播、状态、并发、重复执行和中断恢复。沿调用链确认正常可达的触发条件，不能只猜测空值或构造脱离产品入口的对抗样本。
- 安全性：从实际输入追到危险操作，核对认证授权与秘密暴露，说明可达路径和影响。
- 根因：检查调用方、被调用方和类型约束；判断 guard、重试或强制转换是否掩盖被破坏的契约。
- 维护性：结合项目架构检查职责边界、无谓复杂度和结构退化，说明实际维护成本；个人风格、文件行数或更大重构本身不构成阻塞理由，不动手重构。
- 验证证据：区分用户路径与代理指标，检查行为测试和异步产物的真实证据。没有运行证据时不得声称已复现；普通审核不等于功能验收。
