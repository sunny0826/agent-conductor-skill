# 维护项目验收技能

以功能为覆盖单元，维护由 [生成器](../create-verification-skill/SKILL.md) 或项目现有流程建立的验收技能；找不到目标时指出需先建立验收，不凭空创建维护目标。多个目标且上下文无法确定时澄清。

仅编辑目标验收技能自己的 SKILL、features 与其拥有的 harness，产品回归单独报告，不能改文档掩盖坏行为。

1. 核对功能地图索引与实际文件，修正缺项、重复、死链接和多余条目。
2. 每个功能从源码追踪用户行为。有实际授权委派能力时安排独立只读读者，各返回功能说明、入口、带定位的漂移疑点与一条实跑配方；读者不编辑、不驱动应用。无能力由协调者顺序覆盖并标明非独立。
3. 确保所有功能均有源码结果，核实疑点，合并能共享应用状态的配方。检查最近改动是否增加地图未覆盖的用户入口，须有具体源码。
4. 即使源码看似一致，也逐功能实跑。唯一驱动者按目标 Launch 契约操作：服务或 UI 使用独占的长寿命实例串行驱动，短 CLI 每次独立隔离。首次驱动、每个新会话以及任何异常后重新检查健康与身份；进程健康但 UI 卡死时重置到已知状态或重启。
5. 证据存放在清理范围外，清理后读回。每次失败清理该次残留，不终止他人实例。健康检查本身漂移时在本技能目录修复、只重启受影响部分并重试一次；再失败报告 blocked。harness 修复必须重新实跑。
6. 功能不可达须记录具体权限、认证、OS 或外部前提和已尝试路径，标 verified-unreachable，不能计为已跑通；遗漏前提则修文档。行为正确但无法驱动是 harness 缺口，产品确实坏了是产品问题。
7. 最后一次证明后才完成本次实例清理。交付 clean（每个功能有源码与实跑覆盖且无修正）、changed（有已证明的文档／harness 修正）或 blocked（覆盖未完成），附逐功能和逐入口状态、证据及阻塞。

保留简短工作记录。已有开 PR 授权时最多一个 PR 包含已证明的修正；否则交付本地可评审改动，不自动提交、推送或开 PR。缺实跑能力不能宣称 clean。
