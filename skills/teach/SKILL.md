# 解释到能理解

说明它是什么、怎样工作、为什么这样设计，以读者的问题和已有理解决定重点。

1. 从对话判断读者为何询问、需要理解什么，不用测验索取背景，也不重复读者已知道的部分。
2. 使用包内 [how](../how/SKILL.md) 追踪机制，使用 [why](../why/SKILL.md) 追溯动机。子系统通常需要二者，窄问题可只用相关部分。why 默认将问题明确限定到具体选择和相关来源，让它按契约记录未搜索类别；动机是重点时扩大取证。独立工具任务可并行；没有委派能力就直接调查，不伪称独立探索。
3. 综合原始材料，保留 why 的证据分层和必要犹疑。先用一两句说明定义和本项目用途，给最小完整解释，再按读者追问加深。列函数和常量是索引，不能代替解释机制和取舍。
4. 保持对话，不当讲座。自然停下让读者回应，不打印“暂停”“关键洞见”等表演式标签，不要求复述。无人互动的一次性交付仍要完整。
5. 图帮助理解时使用图。三项以上交互逐步构建几张图，每张重画前一张并增加一个关键关系，不将所有关系塞进最后一张。结构和数据流可用 Mermaid；空间、重叠、布局或前后差异用适合的可视化／图像工具，工具不实际可用时采用能表达同一关系的方式并说明限制。单一事实无需配图。

按包内 [unslop](../unslop/SKILL.md) 写清楚，保留技术名称和证据强度，适配读者语言。交付解释本身，不交付“我做了哪些步骤”的报告。
