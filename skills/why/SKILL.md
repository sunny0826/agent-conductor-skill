# Why · 追溯设计动机

回答“为什么当时这样设计”，与解释当前运行机制不同。默认为只读调查，不修改产品、发送消息或写入外部系统。

## 锚定问题

确定代码位置、符号、版本与待解释的选择。用本地 `git blame -L`、`git log --follow -p`、`git log -S/-G` 与 `git show` 追溯引入及后来改变；从提交消息取得 PR、工单和事件线索。有实际可用的源码平台工具才继续读取 PR 讨论，不能假定 gh 或某个 MCP 已认证。机制不清时使用包内 [how](../how/SKILL.md)。

## 映射来源并调查

从当前可调用工具的描述和权限识别七类来源：源码历史、工单、长文档、聊天、运行监控、错误追踪、产品分析／仓库。按 [来源手册](references/source-playbook.md) 选择相关检索路径；默认逐类检查覆盖情况。不可用、无访问权、未搜索、搜索无结果与有证据表明不相关，是不同状态。用户限制范围时记录限制，不假称完整七类调查。

有实际委派能力时按来源分工，使用 [调查请求](references/investigator-prompt.md)，只授予所需读取能力；否则顺序调查同样保留查询和原始证据。跨来源线索交还协调者。防御代码额外追踪事件与事后报告，保留时间线；不把时间相关当作因果。取完整讨论／文档而非预览；使用真实工具 schema，手册中的厂商工具名只作历史示例，不直接假定可调用。查询有界、只读，表名和列先确认，不复制组织特定 schema。

## 综合并核对

按 [综合请求](references/synthesizer-prompt.md) 阅读所有调查结果，核对引用，保留矛盾与较早版本的约束，避免用今天的干净代码反推过去动机。遵循 [证据分层](references/epistemics.md)：Direct 作者明说、Supported 多证据支持、Inferred 合理推导、Speculative 待证假设、Unknown 未知。每个因果主张附来源与对应语气；搜不到不能证明不存在，用户猜测也只是假设。

交付问题与代码锚点、有分层的结论、证据、矛盾、七类覆盖和缺口。用于后续变更时提炼应保留、可改变、应避免与风险约束，不能把猜测升级为硬要求。调查结束不自动触发实现、提交或外部操作。来源见 [说明](references/sources.md)。
